# 02 — Technical Architecture

This document specifies **the full technical stack and how the pieces fit together**. It is the contract between the spec and the code. Cursor or Antigravity reading this file should know exactly how to scaffold the project, where every file lives, and how data flows from one service to another.

---

## 1. Stack overview

| Layer | Choice | Why |
|-------|--------|-----|
| **Framework** | Next.js 15 (App Router) | Best-in-class SEO via static generation and metadata API; Vercel-native; well-supported by Cursor/Antigravity |
| **Language** | TypeScript (strict mode) | Type safety, better AI tool comprehension, easier refactoring |
| **Styling** | Tailwind CSS v4 | Design tokens live in CSS, atomic utilities, no runtime overhead |
| **UI components** | shadcn/ui (copied into repo) | Open source, customizable, no version lock-in |
| **Forms** | React Hook Form + Zod | Industry standard, accessible, type-safe validation |
| **Email service** | MailerLite | Free up to 1,000 subscribers, supports PDF auto-delivery, simple API |
| **Hosting** | Vercel | Native Next.js support, free tier sufficient, automatic HTTPS, edge network |
| **Domain registrar** | Cloudflare Registrar | Wholesale pricing, no markup, free DNS |
| **DNS + Analytics** | Cloudflare | Free Web Analytics, privacy-friendly (no cookie banner needed) |
| **Repo** | GitHub | Private repository, integrates with Vercel |
| **Node version** | 22.x LTS | Current stable, supported by Next.js 15 |
| **Package manager** | pnpm | Faster than npm, smaller node_modules |

**Important non-choices:**

- **No CMS.** Articles are written as MDX files in the repo. Easier to version-control, no database, no admin UI to maintain.
- **No database.** All content is static. Emails are stored in MailerLite, not in our own database.
- **No authentication.** This is a public marketing site. No user accounts.
- **No analytics requiring cookies.** Cloudflare Web Analytics is GDPR-friendly without a banner.
- **No tracking pixels** (Facebook, TikTok, etc.). Not aligned with the audience's trust profile.

## 4. Data flow: email signup

This is the only piece of dynamic behavior on the site. Everything else is static.

```
User on landing page
    │
    │  1. Types email into form
    │  2. Clicks "Send me the playbook →"
    │
    ↓
React Hook Form validates input (Zod schema: must be valid email)
    │
    ↓
POST request to /api/subscribe
    │
    │  Body: { email: "user@example.com" }
    │
    ↓
src/app/api/subscribe/route.ts
    │
    │  1. Validates again (server-side defense in depth)
    │  2. Calls MailerLite API:
    │     - Add subscriber to playbook-subscribers list
    │     - Trigger Welcome + Deliver PDF automation
    │  3. Returns response
    │
    ↓
Response back to client
    │
    │  - On success: 200, show inline success state
    │  - On failure: 4xx/5xx, show user-friendly error
    │
    ↓
MailerLite (independent of our site)
    │
    │  1. Subscriber added to list
    │  2. Automation triggered:
    │     - Email sent with PDF attachment (or PDF link)
    │     - Double opt-in: subscriber clicks confirmation link
    │  3. PDF delivered
```

### API route specification

`src/app/api/subscribe/route.ts`:

- **Method:** `POST` only
- **Request body:** `{ email: string }`
- **Validation:** Zod schema — email must match RFC 5322 regex
- **Success response:** `200 { success: true }`
- **Error responses:**
  - `400 { error: "Invalid email format" }` — Zod validation failed
  - `409 { error: "Already subscribed" }` — MailerLite returns 422 with this reason
  - `500 { error: "Something went wrong, please try again" }` — Any other failure
- **Rate limiting:** 5 requests per IP per minute (use Vercel's edge config or a simple in-memory store)
- **CORS:** Same-origin only (default for App Router API routes)

### MailerLite API integration

MailerLite v2 API. Endpoint: `https://connect.mailerlite.com/api/subscribers`

Request from our server:

```typescript
const response = await fetch('https://connect.mailerlite.com/api/subscribers', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Accept': 'application/json',
    'Authorization': `Bearer ${process.env.MAILERLITE_API_KEY}`,
  },
  body: JSON.stringify({
    email,
    groups: [process.env.MAILERLITE_LIST_ID],
    status: 'unconfirmed',  // Triggers double opt-in
  }),
});
```

The **double opt-in email** is configured inside MailerLite, not in our code. Setup steps in MailerLite dashboard:

1. Create the list `playbook-subscribers`
2. Enable double opt-in for the list (Settings → Double opt-in: ON)
3. Customize the confirmation email template (subject, body, sender name = "Anna Paskini")
4. Create an automation: Trigger = "When subscriber confirms email" → Send email with PDF attached or PDF download link
5. Test the full flow end-to-end with a real email before going live

## 5. Build and deploy pipeline

### Local development

```bash
pnpm install
pnpm dev               # Runs on http://localhost:3000
```

### CI (GitHub Actions)

`.github/workflows/ci.yml` runs on every PR:

- Install dependencies with pnpm
- Run `pnpm lint` (ESLint + Prettier check)
- Run `pnpm typecheck` (`tsc --noEmit`)
- Run `pnpm build` (verify production build succeeds)

No automated tests in the initial spec — a static marketing site doesn't justify the maintenance overhead. If logic complexity grows in `lib/`, add Vitest for unit tests at that point.

### Production deploy (Vercel)

- Every push to `main` branch → automatic deploy to production
- Every PR → automatic preview deploy to a unique URL (useful for sharing drafts)
- Build command: `pnpm build`
- Output directory: `.next` (Vercel knows this for Next.js projects)
- Node version: 22.x (configure in Vercel project settings)

### Post-deploy verification (manual checklist for first deploy)

1. Visit production URL → page loads without console errors
2. Submit test email → check MailerLite dashboard shows new subscriber
3. Confirm test email → check inbox for PDF delivery email
4. Run Lighthouse on production URL → confirm targets met (LCP, CLS, INP)
5. Test mobile rendering on real device (not just DevTools emulator)
6. Verify `robots.txt` and `sitemap.xml` are accessible
7. Submit sitemap to Google Search Console and Bing Webmaster Tools

## 6. Image strategy

### Image types and processing

| Image | Source | Size delivered | Format | Loading |
|-------|--------|----------------|--------|---------|
| Hero PDF mockup | 3D mockup tool (Smartmockups, Placeit, or custom) | 800×1000 @ 1x, 1600×2000 @ 2x | WebP | `priority` (above fold) |
| Book covers (Vol.1, Vol.2) | Existing book cover files | 600×900 @ 1x, 1200×1800 @ 2x | WebP | Lazy |
| Author photo | Photo Berry provides | 600×600 (cropped square) | WebP | Lazy |
| Article hero images | TBD per article | 1200×675 (16:9) | WebP | `priority` if on article page |
| OG default image | Custom-designed | 1200×630 | JPEG (better social compat) | n/a (meta tag only) |
| Documentary photos for landing zigzag blocks | Sourced from Unsplash, Pexels, or commissioned | 800×600 each, ~4 images | WebP | Lazy |

All images served via `next/image`. Next.js generates responsive `srcset` automatically. WebP with JPEG fallback handled by Next.js.

### Image sourcing rules

- **Author photo:** Must be real, candid, not studio. Berry to provide.
- **Documentary photos for the landing page:** Source from Unsplash or Pexels using these search terms: "elderly father hands," "intergenerational family quiet moment," "elderly man window," "father daughter visit." Avoid: smiling stock seniors, clinical settings, posed family portraits.
- **Article hero images:** Per article, see `03-geo-spec.md` for guidance per article.
- **Never use:** AI-generated images of people (uncanny valley issues, plus increasingly restricted on social platforms). AI-generated abstract textures or backgrounds are fine.

### Image attribution

All Unsplash/Pexels photos must include attribution in the page source as an HTML comment near the image: `<!-- Photo: [photographer name] on Unsplash, https://unsplash.com/photos/[id] -->`. This is not legally required by Unsplash but is good practice.

## 7. SEO infrastructure

This section covers what's set up at the architecture level. Article-level SEO is in `03-geo-spec.md`.

### Metadata

Next.js App Router `metadata` API used in every page. Root `app/layout.tsx` defines defaults:

```typescript
export const metadata: Metadata = {
  metadataBase: new URL(process.env.NEXT_PUBLIC_SITE_URL!),
  title: {
    default: 'Anna Paskini — Memory Activities for Men with Dementia',
    template: '%s | Anna Paskini',
  },
  description: 'Free 15-Minute Visit Playbook and a book series of memory activities for men with dementia.',
  openGraph: {
    type: 'website',
    siteName: 'Anna Paskini',
    images: ['/images/og-default.jpg'],
  },
  twitter: {
    card: 'summary_large_image',
  },
  robots: {
    index: true,
    follow: true,
  },
};
```

Each page overrides specific fields. Articles use `BlogPosting` openGraph type instead of `website`.

### Sitemap

Generated by `next-sitemap`:

```javascript
// next-sitemap.config.js
module.exports = {
  siteUrl: process.env.NEXT_PUBLIC_SITE_URL,
  generateRobotsTxt: true,
  changefreq: 'weekly',
  priority: 0.7,
  exclude: ['/api/*'],
};
```

Runs as part of `pnpm build` (`postbuild` script).

### robots.txt

Generated by `next-sitemap`. Contents:

```
User-agent: *
Allow: /
Disallow: /api/

Sitemap: https://annapaskini.com/sitemap.xml
```

No `Disallow` for AI training crawlers (GPTBot, ClaudeBot, etc.). Allowing them is critical for GEO — these crawlers feed the LLM citation system.

### Schema.org JSON-LD

Each page type uses a specific schema generator in `src/components/schema/`. See `03-geo-spec.md` Section 6 for full schema specifications. Architecture-level rule: every page includes at minimum a `WebPage` schema. Articles add `BlogPosting`, `BreadcrumbList`, and `FAQPage`.

## 8. Analytics

### Cloudflare Web Analytics

Free, privacy-friendly, no cookies. Setup:

1. Add the site to Cloudflare Web Analytics dashboard
2. Get the beacon snippet
3. Add to `app/layout.tsx`:

```typescript
import Script from 'next/script';

// Inside <body>:
<Script
  defer
  src="https://static.cloudflareinsights.com/beacon.min.js"
  data-cf-beacon={`{"token": "${process.env.NEXT_PUBLIC_CLOUDFLARE_ANALYTICS_TOKEN}"}`}
/>
```

Tracks: page views, unique visitors, bounce rate, top pages, top referrers, country, device type. No user-level identification.

### Event tracking (for conversion analysis)

We need to track three specific events beyond page views:

1. **Email form submitted successfully** — fires after the API route returns 200
2. **Amazon CTA clicked** — fires on click of any "See on Amazon" button (track which book, which page)
3. **PDF link clicked from email** — tracked by MailerLite, not by our site

Cloudflare Web Analytics doesn't support custom events on the free tier. Options:

- **Option A:** Add Plausible Analytics (€9/month) for custom events. Privacy-friendly alternative to Google Analytics.
- **Option B:** Skip custom event tracking initially. Use Cloudflare data + MailerLite signup count + Amazon Associates dashboard to triangulate. Free.
- **Option C (recommended for launch):** Use Vercel Analytics (free tier, 2,500 events/month). Built into Vercel, supports custom events via `@vercel/analytics`.

`[BERRY DECISION NEEDED]` — Pick A, B, or C before Phase 1 launch.

### UTM parameters on Amazon links

Every Amazon CTA includes UTM params:

```
https://www.amazon.com/dp/XXXXXXXXXX?tag=annapaskini-20&ref=landing-block-3
```

Where `tag=annapaskini-20` is the Amazon Associates ID (if/when registered) and `ref=...` identifies which block/page the click came from. The `ref` parameter doesn't affect Amazon's tracking but lets us inspect it in our own analytics.

## 9. Performance budgets

These are hard targets, not aspirations. Spec compliance requires meeting all of them.

| Metric | Mobile target | Desktop target | How measured |
|--------|---------------|----------------|--------------|
| Lighthouse Performance | ≥ 90 | ≥ 95 | PageSpeed Insights |
| LCP (Largest Contentful Paint) | < 2.5s | < 2.0s | Real User Monitoring or Lighthouse |
| CLS (Cumulative Layout Shift) | < 0.1 | < 0.1 | Lighthouse |
| INP (Interaction to Next Paint) | < 200ms | < 200ms | Real User Monitoring |
| Total page weight (uncompressed) | < 1 MB | < 1.5 MB | Network tab |
| JavaScript bundle (uncompressed) | < 200 KB | < 200 KB | Next.js build output |

### How to hit these

- Use `next/image` for all images (automatic optimization + lazy loading)
- Avoid client components except where strictly needed (forms, accordions). Everything else is server components.
- No third-party scripts beyond Cloudflare Analytics
- All fonts loaded via `next/font/google` with `display: swap`
- Tailwind purges unused CSS automatically in production builds
- No external CSS frameworks (only Tailwind)

## 10. Accessibility minimum

- All interactive elements keyboard-accessible (Tab, Enter, Escape)
- Focus states visible (no `outline: none` without replacement)
- Color contrast meets WCAG 2.1 AA (4.5:1 for normal text, 3:1 for large text)
- All images have meaningful `alt` text or `alt=""` if decorative
- Form fields have associated `<label>` elements (visible or `sr-only`)
- Form errors announced to screen readers via `aria-live` regions
- Semantic HTML throughout: `<article>`, `<section>`, `<nav>`, `<aside>` used correctly
- `<html lang="en">` set on root layout
- Skip-to-content link in header (visually hidden until focused)

Full accessibility patterns are specified in `04-webdesign.md` Section 9.

## 11. Maintenance and updates

### Quarterly maintenance tasks

- Update Next.js, Tailwind, and shadcn/ui to latest minor versions
- Review and update article content where information has changed (dementia care research updates)
- Refresh hero images if engagement drops
- Audit broken external links (use a tool like `linkinator`)

### Annual tasks

- Renew domain (Cloudflare auto-renews if billing is set up)
- Review and update author bio
- Audit all Amazon links (book ASINs occasionally change if KDP republishes)

### Backup strategy

- Source code: GitHub (already version-controlled)
- Email subscriber list: Export from MailerLite quarterly to CSV, store in cloud storage
- PDF file: Stored in repo at `public/pdfs/`, version-controlled

No database to back up. This is intentional simplicity.
